# NVDA MCP Server

![Version](https://img.shields.io/badge/version-0.12.0-blue)
![Platform](https://img.shields.io/badge/platform-Windows%20x64-brightgreen)

The Rust MCP companion for **NVDA MCP Bridge**. It speaks the Model Context Protocol over stdio to an MCP client, discovers the bridge's tool catalog, and forwards each tool call to the NVDA add-on over the authenticated local HTTP bridge.

| | |
|---|---|
| Companion version | `0.12.0` |
| Bridge API level | `1` |
| Bridge protocol | `nvda-bridge-protocol` `1.0.0` |
| Transport to client | MCP over stdio (JSON-RPC 2.0) |
| Transport to NVDA | HTTP on `127.0.0.1:8765` |
| Platform | Windows x64 |

The companion is built and bundled inside the add-on by `scons`; the standalone `nvda-mcp-server.exe` is also attached to each GitHub release. Most users should install it from **NVDA Menu → Tools → NVDA MCP Bridge → Install or Repair MCP Companion...** rather than building it.

## Responsibilities

- Discover tools from `GET /tools` at startup and retry while NVDA is unavailable.
- Validate the bridge protocol version, API level and instance identity.
- Convert bridge tool definitions into MCP tools with titles, input schemas and optional output schemas.
- Inject a unique request id into every bridge action.
- Validate `structuredContent` against the bridge's output schema.
- Forward bridge errors and recovery hints without inventing new error shapes.
- Serve as a single-worker-thread Tokio runtime so it does not compete with NVDA's event loop.

## Requirements

- Windows 10/11 x64.
- NVDA with the `nvdaMcpBridge` add-on installed and running.
- A bridge token generated by the add-on. The companion reads it from the first available location:

  ```text
  NVDA_BRIDGE_TOKEN
  NVDA_TOKEN_PATH
  NVDA_CONFIG_PATH\nvda-mcp-bridge\token.key
  %APPDATA%\nvda\nvda-mcp-bridge\token.key
  %LOCALAPPDATA%\nvda-mcp-bridge\token.key
  %USERPROFILE%\.nvda-mcp-bridge\token.key
  ```

## Configuration

| Variable | Default | Effect |
|---|---|---|
| `NVDA_BRIDGE_URL` | `http://127.0.0.1:8765` | Bridge address |
| `NVDA_BRIDGE_TOKEN` | Auto-discovered | Explicit bridge token |
| `NVDA_BRIDGE_TIMEOUT_SECS` | `15` | HTTP timeout in seconds |
| `NVDA_BRIDGE_CATEGORIES` | all | Comma-separated category allow-list; the only option that removes tools from the catalog |
| `NVDA_BRIDGE_OUTPUT_SCHEMAS` | `0` | Set to `1` to advertise every `outputSchema` in `tools/list` |
| `NVDA_BRIDGE_TOOLS_PAGE_SIZE` | `100` | Maximum tools per `tools/list` page (1–1000) |
| `LOG_LEVEL` | `INFO` | `TRACE`, `DEBUG`, `INFO`, `WARN` or `ERROR` |

Example MCP client entry:

```json
{
  "mcpServers": {
    "nvda": {
      "command": "C:\\Users\\<you>\\AppData\\Local\\Programs\\NVDA MCP Bridge\\bin\\nvda-mcp-server.exe",
      "args": []
    }
  }
}
```

## Build

The repository root owns the release build. Building through SCons also stages the binary and generates the checksum manifest the add-on expects:

```powershell
scons
```

To build and test only the crate:

```powershell
cargo build --release --manifest-path rust_mcp_bridge/Cargo.toml
cargo test --manifest-path rust_mcp_bridge/Cargo.toml
```

The toolchain is pinned in `../rust-toolchain.toml`. The release binary is written to `target/release/nvda-mcp-server.exe`.

## Tests

```powershell
cargo test
```

The suite covers protocol validation, tool catalog translation, error mapping, request ids, pagination and bridge HTTP flows.

## Architecture

```text
MCP client
    │  MCP / stdio
    ▼
nvda-mcp-server.exe
    │  HTTP + X-NVDA-Bridge-Token
    ▼
NVDA MCP Bridge add-on
    │  main-thread executor
    ▼
NVDA APIs
```

For the bridge contract, tool catalog, permissions and end-user installation, see the [repository README](../README.md) and [docs/](../docs/).
